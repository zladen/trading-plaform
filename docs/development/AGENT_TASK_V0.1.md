# Техническое задание для AI-агента

# Развёртывание криптовалютной торговой платформы — V0.1

## 1. Цель проекта

Развернуть с нуля базовую инфраструктуру автоматизированной криптовалютной торговой платформы.

Результат работы — полноценный Monorepo, который:

- запускается локально через Docker Compose;
- содержит работающий Rust Backend;
- содержит работающий React Frontend;
- подключается к PostgreSQL и Redis;
- предоставляет REST API;
- публикует OpenAPI спецификацию;
- поддерживает WebSocket-инфраструктуру;
- имеет базовую систему логирования и мониторинга состояния;
- содержит автоматические проверки и тесты;
- имеет документацию по архитектуре и запуску.

На данном этапе необходимо создать фундамент проекта, не реализуя торговые алгоритмы.

## 2. Обязательные инструкции

Перед началом работы:

1. Прочитать корневой `AGENTS.md`.
2. Проверить текущую структуру репозитория.
3. Проверить существующие конфигурационные файлы.
4. Проверить установленные версии Rust, Node.js, pnpm и Docker.
5. Проверить доступность Docker Engine.
6. Изучить текущие зависимости и не создавать дублирующие конфигурации.
7. Составить краткий план реализации.

Работать непосредственно в текущем репозитории.

Не удалять существующие файлы без необходимости.

Не перезаписывать пользовательские конфигурации и секреты.

Если обнаружены конфликты между существующей структурой и этим заданием, сначала определить безопасный способ интеграции.

## 5. Backend

### 5.1. Архитектура

Создать модульный монолит с разделением ответственности.

Основные слои:

- Domain — бизнес-модели и правила.
- Application — сценарии использования и интерфейсы зависимостей.
- Infrastructure — PostgreSQL, Redis и внешние адаптеры.
- API — HTTP, WebSocket, DTO и маршрутизация.

Зависимости должны направляться внутрь:

```text
API → Application → Domain
Infrastructure → Application / Domain
```

Domain не должен зависеть от Axum, SQLx, Redis или HTTP.

### 5.2. Запуск приложения

Реализовать:

- загрузку конфигурации;
- проверку обязательных переменных окружения;
- инициализацию tracing;
- подключение к PostgreSQL;
- подключение к Redis;
- создание Application State;
- инициализацию Axum Router;
- graceful shutdown;
- обработку SIGINT и SIGTERM.

При недоступности обязательной зависимости приложение не должно сообщать о готовности.

Ошибки конфигурации должны обнаруживаться при старте.

### 5.3. HTTP API

Создать API с версионированием:

`/api/v1`

Обязательные endpoints:

| Метод | Endpoint               | Назначение                          |
| ----- | ---------------------- | ----------------------------------- |
| GET   | `/api/v1/health`       | Проверка работоспособности процесса |
| GET   | `/api/v1/ready`        | Проверка готовности зависимостей    |
| GET   | `/api/v1/info`         | Информация о версии приложения      |
| GET   | `/api/v1/openapi.json` | OpenAPI спецификация                |

Health должен проверять работоспособность процесса без обращения ко всем внешним зависимостям.

Readiness должен проверять доступность PostgreSQL и Redis.

Ответы должны иметь единый формат.

Добавить middleware для:

- request_id;
- HTTP tracing;
- обработки ошибок;
- корректного CORS;
- ограничения размера входящих запросов.

Не открывать CORS для всех источников без необходимости.

### 5.4. WebSocket

Подготовить базовую WebSocket-инфраструктуру.

Создать endpoint:

`/api/v1/ws`

Реализовать:

- установление соединения;
- обработку отключения клиента;
- ping/pong или heartbeat;
- корректное завершение соединения;
- базовую типизацию сообщений.

Пока не реализовывать реальные торговые события и поток рыночных данных.

### 5.5. OpenAPI

Использовать Utoipa.

Обеспечить:

- генерацию OpenAPI из backend;
- актуальность спецификации;
- описание основных endpoints;
- Swagger UI в dev-режиме.

OpenAPI должен стать единственным источником API-контракта для Frontend.

## 6. PostgreSQL и SQLx

Подключить PostgreSQL через SQLx.

Реализовать:

- connection pool;
- конфигурацию пула;
- проверку подключения;
- выполнение миграций;
- обработку ошибок подключения.

Создать начальную миграцию только при наличии необходимой инфраструктурной таблицы.

Не создавать заранее таблицы стратегий, ордеров, сделок и позиций.

Требования:

- SQL-запросы с bind-параметрами;
- транзакции для атомарных операций;
- UTC для времени;
- миграции в `migrations/`;
- никаких SQL-запросов в Domain.

Проверить возможность использования SQLx offline mode, если это удобно для CI.

## 7. Redis

Подключить Redis как вспомогательную инфраструктуру.

На V0.1 реализовать только:

- подключение;
- конфигурацию;
- проверку доступности;
- корректное закрытие соединений.

Не создавать очереди, Pub/Sub, Streams и сложную систему кэширования без конкретной задачи.

Redis не должен становиться источником истины для постоянных данных.

## 8. Frontend

### 8.1. Инициализация

Создать приложение на React + TypeScript + Vite.

Включить строгий TypeScript:

- strict;
- noImplicitAny;
- strictNullChecks;
- noUnusedLocals;
- noUnusedParameters.

Установить и настроить:

- React Router;
- TanStack Query;
- Zustand;
- React Hook Form;
- Zod;
- Tailwind CSS;
- shadcn/ui;
- TradingView Lightweight Charts.

Не создавать сложный интерфейс и лишние страницы.

### 8.2. Feature-Sliced Design

Строго соблюдать FSD.

Слои:

```text
app/
pages/
widgets/
features/
entities/
shared/
```

Настроить алиасы и правила импортов.

Запретить:

- циклические зависимости;
- импорт внутренних модулей чужих срезов;
- нарушение направления зависимостей;
- размещение бизнес-логики в компонентах общего назначения.

### 8.3. Dashboard

Создать стартовую Dashboard-страницу.

Она должна отображать:

- состояние Backend;
- состояние PostgreSQL;
- состояние Redis;
- версию Backend;
- состояние WebSocket;
- общее состояние системы.

Получать информацию через реальные API endpoints.

Не использовать фиктивные данные для имитации работающей инфраструктуры.

Предусмотреть состояния:

- Loading;
- Success;
- Error;
- Unavailable.

Добавить кнопку повторной проверки состояния.

Интерфейс должен быть адаптивным и иметь базовую тёмную тему.

### 8.4. API Client

Организовать единый API client в `shared`.

Требования:

- единая конфигурация base URL;
- обработка ошибок;
- типизированные запросы;
- поддержка отмены запросов;
- корректная обработка HTTP-статусов.

Сгенерировать TypeScript-типы и API client из OpenAPI.

Не дублировать вручную типы backend API.

## 9. Docker Compose

Создать `compose.yaml` в корне проекта.

Сервисы:

- backend;
- frontend;
- postgres;
- redis.

Требования:

- отдельные Dockerfile;
- multi-stage build там, где это оправдано;
- healthcheck для всех необходимых сервисов;
- named volumes для PostgreSQL и Redis;
- внутренняя Docker network;
- PostgreSQL и Redis не должны публиковаться на внешний интерфейс;
- frontend и backend должны запускаться независимо;
- корректный порядок запуска зависимостей;
- возможность перезапуска сервисов.

Настроить переменные окружения через `.env`.

Добавить `.env.example` без реальных секретов.

Не использовать `latest` для базовых образов в production-конфигурации.

Не запускать контейнеры от root без технической необходимости.

## 10. Конфигурация

Реализовать централизованную конфигурацию Backend.

Пример переменных:

```env
APP_ENV=development
APP_HOST=0.0.0.0
APP_PORT=8080

DATABASE_URL=postgres://platform:password@postgres:5432/platform

REDIS_URL=redis://redis:6379

RUST_LOG=info
FRONTEND_URL=http://localhost:5173

VITE_API_URL=http://localhost:8080
```

Значения в примере являются демонстрационными.

Не хранить реальные пароли и токены в репозитории.

Не включать `.env`, `secrets/` и приватные ключи в Git.

Не читать секреты GitHub MCP из приложения. MCP-конфигурация и секреты OpenCode не относятся к runtime-конфигурации платформы.

## 16. Безопасность

На V0.1:

- не реализовывать торговые API-ключи;
- не реализовывать JWT;
- не реализовывать регистрацию пользователей;
- не открывать внутренние порты БД и Redis наружу;
- не хранить секреты в Git;
- использовать минимальные права контейнеров;
- валидировать внешние данные;
- не допускать утечки секретов через логи.

Архитектура должна позволять добавить авторизацию на следующем этапе.

## 17. Что запрещено реализовывать

- интеграции с криптовалютными биржами;
- Spot Trading;
- Futures Trading;

- технические индикаторы;

- Backtesting;
