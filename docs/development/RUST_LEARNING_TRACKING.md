# Rust Learning Tracking & Assessment

> Система проверки заданий и учёта прогресса обучения Rust.
>
> Этот документ является обязательной инструкцией для AI-агента при обучении пользователя Rust и разработке торговой платформы.

---

# 1. Назначение документа

AI-агент обязан использовать этот документ для:

1. Проверки выполненных учебных заданий.
2. Проверки проектных изменений.
3. Независимой оценки технического качества кода.
4. Независимой оценки знаний пользователя.
5. Учёта результатов каждого занятия.
6. Выявления тем, требующих повторения.
7. Управления переходом к следующим занятиям.

Программа обучения находится в:

`docs/development/RUST_LEARNING_PLAN.md`

Общие правила поведения агента находятся в:

`AGENTS.md`

Текущий технический этап разработки определяется соответствующим техническим заданием проекта.

## Основной принцип

Каждое занятие имеет два независимых результата:

- Technical Assessment — качество реализации.
- Learning Assessment — уровень понимания пользователя.

Занятие считается полностью завершённым только после успешного прохождения обеих проверок.

Высокая техническая оценка не компенсирует недостаточное понимание кода пользователем.

---

# 2. Состояния учебного задания

Каждое занятие может находиться в одном из следующих состояний:

| Статус           | Значение                                         |
| ---------------- | ------------------------------------------------ |
| NOT_STARTED      | Занятие ещё не начато                            |
| IN_PROGRESS      | Пользователь выполняет задание                   |
| TECHNICAL_REVIEW | Выполняется проверка кода                        |
| TECHNICAL_REWORK | Требуется исправление реализации                 |
| LEARNING_REVIEW  | Проверяются знания пользователя                  |
| LEARNING_REWORK  | Требуется повторение темы                        |
| BLOCKED          | Проверка заблокирована внешними обстоятельствами |
| ACCEPTED         | Обе проверки успешно пройдены                    |

Допускается переход между состояниями:

```text
NOT_STARTED
    |
    v
IN_PROGRESS
    |
    v
TECHNICAL_REVIEW
    |
    +----> TECHNICAL_REWORK
    |             |
    |             +----> TECHNICAL_REVIEW
    |
    v
LEARNING_REVIEW
    |
    +----> LEARNING_REWORK
    |             |
    |             +----> LEARNING_REVIEW
    |
    v
ACCEPTED
```

Если техническая проверка не пройдена, учебная проверка не проводится до исправления критических технических проблем.

Если техническая проверка пройдена, но учебная нет, код можно принять технически, однако занятие остаётся незавершённым.

# 3. Technical Assessment — техническая оценка

Максимальная оценка: 100 баллов.

## 3.1. Критерии оценки

| Критерий                         | Максимум |
| -------------------------------- | -------: |
| Соответствие требованиям задания |       25 |
| Корректность реализации          |       20 |
| Архитектура и соблюдение границ  |       15 |
| Обработка ошибок и безопасность  |       10 |
| Читаемость и качество кода       |       10 |
| Unit и Integration Tests         |       15 |
| Отсутствие регрессий             |        5 |
| **Итого**                        |  **100** |

Если критерий неприменим к конкретному заданию, перераспредели его вес пропорционально между применимыми критериями. Обязательно укажи это в отчёте.

## 3.2. Порог прохождения

Для успешной технической приёмки необходимо:

- Не менее 85 баллов.
- Отсутствие критических ошибок.
- Выполнение обязательных требований задания.
- Успешное прохождение применимых проверок.
- Отсутствие нарушений архитектурных ограничений.

## 3.3. Что проверять

Перед оценкой изучи:

1. Исходное задание и его критерии приёмки.
2. Текущий Git diff.
3. Изменённые файлы.
4. Существующую реализацию связанных компонентов.
5. Архитектурные инструкции проекта.
6. Существующие тесты.

Проверяй:

- Корректность Rust-кода.
- Правильное использование Ownership и Borrowing.
- Обработку ошибок через Result и Option.
- Отсутствие ненужных unwrap() и expect().
- Отсутствие ненужного клонирования.
- Использование подходящих типов.
- Корректность асинхронного кода.
- Отсутствие ненужных блокировок и проблем конкурентного доступа.
- Соблюдение Domain / Application / Infrastructure.
- Наличие тестов.
- Отсутствие регрессий.

Дополнительные обязательные ограничения торговой платформы:

- Финансовые вычисления используют rust_decimal, а не f64.
- Время хранится и обрабатывается в UTC.
- Domain не зависит от Axum, SQLx и конкретных биржевых адаптеров.
- Стратегии не размещают ордера напрямую.
- Risk Engine отвечает за централизованную проверку рисков.
- Execution Engine отвечает за исполнение операций.

Учитывай применимость каждого ограничения к конкретному заданию.

## 3.4. Команды проверки

Для Rust Workspace используй подходящие команды:

```bash
cargo fmt --all -- --check

cargo check --workspace

cargo clippy --workspace --all-targets --all-features -- -D warnings

cargo test --workspace
```

Если в проекте предусмотрены дополнительные команды, используй их.

Не запускай проверки, способные повредить пользовательские или production-данные.

Обязательно фиксируй:

- Какую команду запустил.
- Успешно ли она завершилась.
- Если произошла ошибка — её причину.
- Если команда не запускалась — почему.

Запрещено утверждать, что тесты или проверки прошли, если они фактически не выполнялись.

# 4. Learning Assessment — оценка знаний

Максимальная оценка: 100 баллов.

## 4.1. Критерии оценки

| Критерий                        | Максимум |
| ------------------------------- | -------: |
| Понимание теории и терминологии |       25 |
| Понимание собственного кода     |       25 |
| Понимание архитектурных решений |       15 |
| Самостоятельное изменение кода  |       25 |
| Поиск и исправление ошибок      |       10 |
| **Итого**                       |  **100** |

## 4.2. Порог прохождения

Для успешной учебной приёмки необходимо:

- Не менее 80 баллов.
- Правильное понимание основных концепций занятия.
- Способность объяснить собственный код.
- Успешное выполнение самостоятельного практического изменения.
- Понимание основных ошибок, связанных с изучаемой темой.

Не требуй знания терминов наизусть. Оценивай реальное понимание.

## 4.3. Этапы проверки знаний

### Этап A. Теоретические вопросы

Задай пользователю 3–5 вопросов.

Вопросы должны проверять понимание, а не простое воспроизведение определений.

Например, для Ownership:

- Что происходит с String при передаче его в функцию?
- Чем отличается передача значения от передачи ссылки?
- В каких случаях используется &mut?
- Почему Rust запрещает одновременное наличие определённых ссылок?
- Что произойдёт при попытке использовать переменную после move?

Не показывай правильные ответы до попытки пользователя.

### Этап B. Понимание собственного кода

Выбери 2–3 фрагмента из выполненного задания.

Попроси пользователя объяснить:

- Что делает код.
- Какие конструкции Rust используются.
- Почему выбраны конкретные типы.
- Как работает передача владения.
- Почему использованы ссылки или клонирование.
- Как обрабатываются ошибки.
- Какие альтернативные решения существуют.

Не задавай вопросы о концепциях, которые ещё не изучались.

### Этап C. Самостоятельное изменение

Предложи небольшое практическое изменение к уже написанному коду.

Например:

- Добавить новый метод.
- Изменить функцию с передачи владения на передачу ссылки.
- Добавить новый вариант enum.
- Обработать дополнительную ошибку.
- Добавить тест для граничного случая.
- Изменить алгоритм обработки коллекции.

Пользователь должен самостоятельно написать изменение.

Разрешено использовать документацию Rust.

Не выдавай готовое решение до попытки пользователя.

**Изменение строится только на пройденном материале.** Этап C подчиняется §2.1
`RUST_LEARNING_PLAN.md` точно так же, как учебное задание. Если для изменения
нужны `let`, `mut`, `const`, функции с параметрами, ссылки, `Option`/`Result`,
коллекции или любая другая непройденная конструкция — такое изменение выдавать
нельзя.

Проверь перед выдачей: каждая конструкция в решении должна быть либо пройдена,
либо изучаться в этот же день. Если подходящего изменения на пройденном
материале нет, это означает, что оценивать самостоятельную практику ещё рано:
оцени Этап C как неприменимый и перераспредели вес, а не подсовывай
непройденный синтаксис.

Допустимый пример для Дня 1 (доступны `println!` и литералы): изменить текст
вывода, добавить третью строку с другим литералом, поменять порядок строк.

### Этап D. Исправление ошибки

Предложи небольшую ошибку в учебном коде или попроси пользователя самостоятельно найти проблему в существующей реализации.

Пользователь должен:

1. Найти проблему.
2. Объяснить причину.
3. Предложить исправление.
4. Проверить исправление.

Если задание не предусматривает подходящей ошибки, этот критерий можно оценить по анализу реальной ошибки из предыдущей практики.

# 5. Система подсказок

Во время учебной проверки используй последовательные подсказки.

| Уровень | Помощь                                              |
| ------- | --------------------------------------------------- |
| 1       | Указать направление поиска                          |
| 2       | Напомнить соответствующую концепцию                 |
| 3       | Показать аналогичный небольшой пример               |
| 4       | Подробно объяснить решение                          |
| 5       | Показать готовую реализацию по просьбе пользователя |

Если пользователь получил готовое решение от агента, не засчитывай соответствующую часть практики как самостоятельное выполнение.

После объяснения предложи аналогичное, но немного изменённое задание.

Помощь не должна превращать проверку в угадывание правильного ответа.

---

# 6. Итоговая приёмка

Для полного принятия задания должны **одновременно** выполняться все условия:

| Условие                      | Требование      |
| ---------------------------- | --------------- |
| Technical Assessment         | Не менее 85/100 |
| Learning Assessment          | Не менее 80/100 |
| Критические ошибки           | Отсутствуют     |
| Обязательные тесты           | Пройдены        |
| Самостоятельное изменение    | Выполнено       |
| Понимание ключевых концепций | Подтверждено    |
| Результат в файле прогресса  | Зафиксирован    |

Если хотя бы одно условие не выполнено, занятие не принимается и переход к
следующему занятию запрещён.

Оценки не суммируются и не усредняются. `95/100` и `75/100` — это не «85 в
среднем» и не пройденная проверка: техническая часть принята, учебная — нет,
статус `LEARNING_REWORK`.

Технически принятый код остаётся в репозитории и не откатывается: проблема
касается освоения темы, а не качества реализации.

## 6.1. Возможные результаты

### ACCEPTED

Обе оценки достигли необходимых порогов.

- Техническая работа принята.
- Учебная тема освоена.
- Занятие завершено.
- Разрешён переход к следующему занятию.

### TECHNICAL_REWORK

Техническая оценка ниже 85.

- Указать конкретные проблемы.
- Сформировать план исправлений.
- Не проводить финальную учебную проверку.
- После исправлений повторить техническую проверку.

### LEARNING_REWORK

Техническая оценка пройдена, учебная ниже 80.

- Не отменять техническую приёмку корректного кода.
- Зафиксировать слабые места.
- Дать дополнительные упражнения.
- Повторно проверить знания.
- Не переходить к следующему занятию до успешной пересдачи.

### BLOCKED

Проверка невозможна.

Например:

- Нет доступа к PostgreSQL.
- Не установлены необходимые зависимости.
- Не работает тестовое окружение.
- Отсутствуют необходимые данные.

Не выставляй фиктивные оценки. Укажи причину и способ устранения блокировки.

# 7. Формат отчёта по каждому занятию

После проверки всегда формируй отчёт следующего вида:

## Lesson Assessment

**Занятие:** Неделя X, День Y.

**Тема:** Название темы.

**Статус:** ACCEPTED / TECHNICAL_REWORK / LEARNING_REWORK / BLOCKED.

### Technical Assessment

**Оценка: X/100**

| Критерий              | Баллы |
| --------------------- | ----: |
| Требования            |  X/25 |
| Корректность          |  X/20 |
| Архитектура           |  X/15 |
| Ошибки и безопасность |  X/10 |
| Качество кода         |  X/10 |
| Тесты                 |  X/15 |
| Регрессии             |   X/5 |

**Проверенные файлы:**

- Список файлов.

**Выполненные команды:**

- Команда и результат.

**Найденные проблемы:**

- Список замечаний или отсутствие замечаний.

### Learning Assessment

**Оценка: X/100**

| Критерий                  | Баллы |
| ------------------------- | ----: |
| Теория                    |  X/25 |
| Понимание кода            |  X/25 |
| Архитектура               |  X/15 |
| Самостоятельное изменение |  X/25 |
| Работа с ошибками         |  X/10 |

**Что пользователь понял:**

- Список освоенных концепций.

**Что требует повторения:**

- Список слабых мест.

**Результат практического задания:**

- Что сделал пользователь самостоятельно.

### Итог

**Техническая приёмка:** пройдена / не пройдена.

**Учебная приёмка:** пройдена / не пройдена.

**Следующее действие:**

- Следующее занятие.
- Или дополнительное упражнение.
- Или исправление кода.

# 8. Учёт прогресса

Основной файл прогресса:

`docs/development/RUST_LEARNING_PROGRESS.md`

Агент обязан обновлять его после каждой завершённой проверки.

## 8.1. Что хранить

- Текущую неделю.
- Текущий учебный день.
- Статус текущего задания.
- Последнее принятое занятие.
- Техническую оценку.
- Учебную оценку.
- Выполненные проектные задачи.
- Проверенные файлы.
- Результаты тестов.
- Ошибки и замечания.
- Темы для повторения.
- Историю пересдач.
- Следующее разрешённое занятие.

## 8.2. Правила обновления

1. Не отмечай занятие завершённым до прохождения обеих проверок.
2. Не изменяй результаты предыдущих занятий задним числом.
3. Сохраняй историю всех попыток.
4. Если тема не усвоена, добавляй её в список повторения.
5. Если пользователь повторно ошибается в одной концепции, увеличивай количество практических упражнений по этой теме.
6. Не переходи к следующему занятию автоматически без подтверждения результатов.
7. При начале новой сессии сначала прочитай файл прогресса.
8. Если результаты Git или тестов изменились после приёмки, не переписывай историю: зафиксируй отдельное событие повторной проверки.

# 10. Правила определения следующего занятия

При запуске новой учебной сессии:

1. Прочитай AGENTS.md.
2. Прочитай RUST_LEARNING_PLAN.md.
3. Прочитай RUST_LEARNING_PROGRESS.md.
4. Проверь текущий статус последнего занятия.
5. Определи следующее разрешённое занятие.

Если статус ACCEPTED — можно предложить следующее занятие.

Если статус TECHNICAL_REWORK — продолжай исправление реализации.

Если статус LEARNING_REWORK — продолжай обучение текущей теме.

Если статус BLOCKED — помоги устранить блокировку.

Если файл прогресса отсутствует, создай его с начальной позицией Week 1, Day 1.

Не определяй прогресс по истории переписки, если он уже зафиксирован в файле.

Файл прогресса является основным источником состояния обучения.

# 11. Правила взаимодействия с пользователем

Этот раздел — **канонический** список команд. Остальные документы ссылаются на
него и не должны содержать собственный вариант списка.

| Команда                 | Действие                                                          |
| ----------------------- | ----------------------------------------------------------------- |
| Начать обучение         | Выдать первое незавершённое занятие                               |
| Следующее занятие       | Выдать следующее разрешённое занятие                              |
| Объясни тему            | Объяснить текущую концепцию подробнее, без готового решения задачи |
| Дай подсказку           | Дать следующую подсказку по текущей задаче                        |
| Проверь задание         | Запустить Technical Assessment                                     |
| Проверь знания          | Запустить Learning Assessment, если техническая проверка пройдена  |
| Проведи полную проверку | Выполнить обе проверки по порядку                                 |
| Повтори тему            | Сформировать дополнительные упражнения                            |
| Покажи прогресс         | Показать текущее состояние обучения                               |
| Покажи оценки           | Показать историю Technical и Learning оценок                      |
| Проверь код             | Провести Code Review изменений                                    |
| Адаптируй программу     | Скорректировать дальнейший план                                   |

Перед выполнением любой команды сначала прочитай
`docs/development/RUST_LEARNING_PROGRESS.md` и проверь фактическое состояние
файлов. Не определяй текущую позицию по истории переписки.

`Проверь задание` и `Проверь знания` — **разные** команды с разными порогами.
`Проверь задание` не выставляет Learning Assessment и не может завершить занятие.
`Проведи полную проверку` запускает их последовательно: техническая сначала,
учебная — только после прохождения технической.

Если пользователь просит выполнить задание полностью, разрешается помочь с реализацией.

Однако выполненная агентом работа не засчитывается как доказательство самостоятельного освоения темы.

# 12. Адаптация программы

Учебная программа является последовательной, но не должна быть абсолютно жёсткой.

Если пользователь не усвоил тему:

- Не переходи к более сложным концепциям, зависящим от неё.
- Добавь дополнительные упражнения.
- Измени сложность заданий.
- Используй примеры из торговой платформы.
- Повторно проверь знания.

Если пользователь хорошо освоил тему:

- Не создавай искусственные дополнительные задания.
- Можно сократить повторение.
- Сохраняй обязательные контрольные точки.

Если разработка проекта опережает обучение:

- Не позволяй агенту бесконтрольно использовать незнакомые концепции.
- Объясняй новый код до принятия пользователем изменений.
- При необходимости создавай отдельные учебные упражнения.

Если проект отстаёт от учебного плана:

- Не создавай ненужную функциональность ради соответствия календарю.
- Переноси проектную часть на актуальные задачи.
- Сохраняй изучение Rust в отдельном учебном проекте.

# 14. Ветки и Git-дисциплина

Каждое занятие выполняется в отдельной ветке. Работа напрямую в `main` для
учебных задач запрещена.

## 14.1. Именование

```text
lesson/<week>-<day>-<short-topic>
```

Примеры:

```text
lesson/01-01-cargo-setup
lesson/01-02-variables
lesson/02-03-references
```

Проектные задачи вне учебного плана используют отдельный префикс:

```text
task/<short-topic>
```

Используй только строчные латинские буквы, цифры и дефис. Кириллица и пробелы в
имени ветки недопустимы.

## 14.2. Порядок работы

1. Убедись, что рабочее дерево чистое (`git status`).
2. Обнови `main`: `git switch main && git pull --ff-only`.
3. Создай ветку занятия от актуального `main`.
4. Выполни задание и проверки.
5. Зафиксируй результат коммитом.
6. Отправь ветку: `git push -u origin <branch>`.
7. После `ACCEPTED` ветка сливается в `main`.

Не начинай занятие на грязном дереве: незакоммиченные изменения из предыдущего
занятия смешаются с новым и сломают и Code Review, и обе оценки.

## 14.3. Запрещено

- Коммитить напрямую в `main` (кроме инфраструктурных правок, не относящихся к
  занятию).
- Переписывать историю уже отправленной ветки (`push --force`) без явной просьбы.
- Мержить ветку занятия до статуса `ACCEPTED`.
- Коммитить `.env`, `secrets/`, ключи и реальные учётные данные.

## 14.4. Связь с оценками

`ACCEPTED` выставляется по содержимому ветки, а не по описанию. Перед проверкой:

- ветка существует и отправлена;
- коммиты относятся только к текущему занятию;
- `git status` чистый;
- проверки запускались на этой ветке.

Если код в ветке не соответствует тому, что проверялось, оценка не выставляется —
статус `BLOCKED` с указанием причины.

## 14.5. Запись в файле прогресса

Для каждой ветки фиксируй:

- имя ветки;
- коммит (короткий хеш);
- статус (`IN_PROGRESS`, `TECHNICAL_REWORK`, `LEARNING_REWORK`, `ACCEPTED`, `BLOCKED`);
- дату слияния в `main` после `ACCEPTED`.

Формат записи:

```text
| Lesson  | Branch                  | Commit  | Status   | Merged |
| ------- | ----------------------- | ------- | -------- | ------ |
| 01-01   | lesson/01-01-cargo-setup | a2a3253 | ACCEPTED | yes    |
```

## 14.6. Время ожидания CI

CI запускается на каждый push в любую ветку и на pull request. В этом репозитории
запуск появляется с задержкой в несколько минут (наблюдалось до ~3 минут), а полный
прогон занимает примерно столько же — четыре job'а, включая `infrastructure`,
который поднимает Docker Compose и выполняет smoke-тест.

Практические следствия:

- Не жди результата сразу после `git push`.
- Не перезапускай CI «на всякий случай»: параллельные запуски на одну ветку
  отменяются настройкой `concurrency`.
- Если нужен немедленный прогон, используй `gh workflow run CI` и следи за
  `gh run watch`.
- Не считай задание проверенным, пока CI не завершился успешно или пока не указана
  причина, по которой он не мог быть запущен.

## Главный критерий успеха

Цель программы — не просто получить работающую торговую платформу.

Пользователь должен постепенно научиться самостоятельно:

- Читать Rust-код.
- Понимать Ownership и Borrowing.
- Проектировать структуры и интерфейсы.
- Работать с Tokio и асинхронностью.
- Разрабатывать API на Axum.
- Работать с PostgreSQL через SQLx.
- Писать тесты.
- Проводить Code Review.
- Принимать архитектурные решения.

**Техническое качество проекта и самостоятельные знания пользователя являются двумя обязательными и независимыми результатами обучения.**
